# خطة تطوير وتحديث نظام رحلات التوافق وسداد العربون وإدارة الطلبات

خطة شاملة ومتكاملة لتحسين تجربة المستخدم ولوحة الإدارة معاً، تبسيط مسار رحلة التوافق، إزالة العناصر والنوافذ المعرقلة، إصلاح خلل احتساب السداد المبكر، وتزويد الإدارة بأدوات مرنة للتحكم بحالة ومبالغ سداد العربون.

## قرارات المستخدم المعتمدة

> [!IMPORTANT]
> تم تأكيد الخيارات التالية من قِبل المستخدم في مرحلة التوضيح والاستبيان:

- **ترتيب التنفيذ**: تنفيذ وتحديث الكل معاً (تحسين تجربة العضو والرحلة بالتوازي مع لوحة تحكم الإدارة).
- **النافذة المنبثقة عند القبول**: حذف نافذة التهنئة المنبثقة (`AcceptedCelebrationModal`) بالكامل والانتقال السلس والمباشر إلى صفحة الرحلة.
- **تصميم مراحل الرحلة**: اعتماد خط مراحل مبسط، عصري وسهل يتألف من 3 مراحل أساسية واضحة (إرسال الطلب، القبول وسداد العربون، جاري التنسيق والتواصل) ومرحلة نهائية مكتملة مباركة.

---

## 1. نظرة عامة والهدف الرئيسي

- **المشكلة الحالية**:
  1. وجود أزرار زائدة لا فائدة منها تربك المستخدم وتكرر عناصر التنقل.
  2. ظهور نافذة منبثقة معرقلة عند قبول طلب التوافق تقطع تدفق المستخدم بدلاً من نقله مباشرة لخطوته التالية.
  3. استمرار ظهور خط المراحل بطريقة الـ 7 مراحل القديمة المربكة بصرياً بدلاً من المسار المبسط الحديث.
  4. خلل برمجي جسيم: عند طلب عضو للتوافق وقبول الطرف الآخر للطلب، يظهر النظام تلقائياً أنه تم سداد جزء من المبلغ أو العربون رغم عدم قيام أي منهما بالسداد الفعلي.
  5. نقص في مرونة لوحة الإدارة لمتابعة حالة سداد العربون وتحديد ما إذا كان العضو مسدداً أو بانتظار السداد أو غير مسدد، مع إمكانية إدخال وتعديل المبلغ الفعلي المسدد.

- **القيمة المضافة**:
  تجربة مستخدم مريحة، واضحة وخالية من التناقضات المالية أو الأزرار الزائدة، مع إحكام كامل ودقيق لمدفوعات العربون من قبل إدارة المنصة.

---

## 2. تجربة المستخدم والتصميم البصري (UX & UI)

### أ. مسار العضو (رحلة التوافق)
1. **القبول المباشر دون مقاطعة**:
   - عند الضغط على "قبول طلب التوافق"، يتم تحديث الحالة في الخلفية وتوجيه العضو فوراً إلى صفحة الرحلة الخاصة بهذا الطلب مع إشعار نجاح فوري وخفيف (Toast).
   - إلغاء ظهور `AcceptedCelebrationModal` تماماً لعدم تشتيت العضو.
2. **حذف الزر الزائد**:
   - إزالة زر العودة المكرر في أسفل بطاقة الرحلة، والاعتماد على شريط التنقل العلوي الواضح المتناسق.
3. **خط المراحل المبسط والحديث (Journey Stepper & Timeline)**:
   - إلغاء الـ 7 مراحل القديمة في كل من `JourneyPage.tsx` و `JourneyTimeline.tsx` و `AdminRequests.tsx`.
   - اعتماد 3 محطات أساسية متسلسلة + خطوة الإتمام النهائية:
     1. **① إرسال الطلب**: (بانتظار رد الطرف الآخر).
     2. **② القبول وسداد العربون**: (تم القبول، بانتظار سداد الطرفين لعربون الجدية 1,000 ر.ق لكل طرف وتأكيد الإدارة).
     3. **③ جاري التنسيق والتواصل**: (العربون مسدد، الإدارة تتولى التنسيق والتوفيق والترتيب الشرعي).
     4. **👑 تمام النصيب والزواج**: (المرحلة المكتملة المباركة بعد تسليم المهر).
   - تصميم خط أفقي عصري مع مؤشرات حالة دقيقة وألوان هادئة ومتوافقة مع المعايير (بدون شارات دائرية مزدحمة أو نصوص مكررة).

### ب. شاشة الإدارة (لوحة تحكم الطلبات والمدفوعات)
1. **أدوات إدارة سداد العربون لكل طرف (المرسل والمستقبل)**:
   - قائمة منسدلة / أزرار اختيار سريعة لحالة السداد لكل عضو:
     - 🟢 **تم السداد** (Paid)
     - 🟡 **بانتظار السداد** (Pending Payment)
     - ⚪ **لم يسدد بعد** (Not Paid)
   - حقل إدخال عددي مخصص للمبلغ المسدد (`المبلغ المسدد ر.ق`) يسمح للمشرف بكتابة وتعديل المبلغ بدقة (مثلاً: 1000، 500، 0، أو أي دفعة).
   - مؤشر مرئي واضح يوضح هل الطرف الأول سدد والطرف الثاني سدد، وإمكانية نقل الطلب لمرحلة "التنسيق والتواصل" بضغطة زر بمجرد اكتمال السداد.

## 3. القرارات التقنية ومعالجة الخلل الجذري

```
┌────────────────────────────────────────────────────────┐
│                   مسار معالجة سداد العربون                │
└────────────────────────────────────────────────────────┘
                          │
  ┌───────────────────────▼──────────────────────────┐
  │  إنشاء طلب التوافق أو قبوله:                       │
  │  sender_paid: false, receiver_paid: false         │
  │  sender_paid_amount: 0, receiver_paid_amount: 0   │
  │  المرحلة: accepted (القبول وبانتظار سداد العربون)    │
  └───────────────────────┬──────────────────────────┘
                          │
  ┌───────────────────────▼──────────────────────────┐
  │  لوحة الإدارة / تأكيد الدفع:                      │
  │  - الإدارة تختار حالة سداد المرسل والمستقبل         │
  │  - الإدارة تسجل المبلغ المسدد بدقة                 │
  │  - عند اكتمال سداد الطرفين تنتقل الرحلة للتنسيق     │
  └──────────────────────────────────────────────────┘
```

### أ. علاج خلل السداد التلقائي الخاطئ
- في `src/lib/data/adapters/local/localStore.ts`:
  - إيقاف تعيين `sender_paid = true` أو `receiver_paid = true` أو افتراض مبالغ 1000 ر.ق عند إنشاء الطلب أو قبوله ما لم تكن هناك عملية دفع مسجلة ومثبتة رسمياً.
  - تنظيف فحص `isMemberDepositPaid`: التأكد من أنه لا يعتبر العضو مسدداً إلا إذا كان السداد مسجلاً بصورة حقيقية ومؤكدة، وليس لمجرد أن العضو مستورد أو تم إنشاؤه مسبقاً.
  - ضبط شروط الانتقال إلى مرحلة `coordination` لكي لا تحدث إلا بعد تأكيد السداد الفعلي من الطرفين أو من قِبل الإدارة.

### ب. توحيد المراحل
- ضبط مصفوفة `JOURNEY_STAGES` لتعتمد المراحل الأربع الصافية، وتحديث جميع الـ mappings والـ indexes في:
  - `src/lib/journey.ts`
  - `src/components/JourneyTimeline.tsx`
  - `src/pages/JourneyPage.tsx`
  - `src/pages/admin/AdminRequests.tsx`

## 4. خطة تنفيذ التعديلات خطوة بخطوة

1. **الخطوة 1: إصلاح نموذج البيانات ومنطق السداد التلقائي (`localStore.ts`)**
   - تعديل دالة `createRequest` لتبدأ دائماً بمبالغ مسددة 0 وحالة سداد غير مكتملة حتى يسدد الطرفان.
   - تعديل دالة `acceptRequest` بحيث عند القبول يبقى الطلب في مرحلة `accepted` (بانتظار سداد العربون) مع مبالغ مسددة 0، ولا ينتقل تلقائياً للتنسيق إلا بسداد الطرفين.
   - إضافة دالة في الـ Store لتحديث حالة سداد العربون والمبلغ المسدد لكل طرف بشكل منفصل:
     `updateRequestDepositPayment(requestId, party: 'sender' | 'receiver', status: 'paid' | 'pending' | 'unpaid', amount: number)`.

2. **الخطوة 2: حذف النافذة المنبثقة والزر الزائد (`InterestRequests.tsx` & `JourneyPage.tsx`)**
   - في `src/pages/InterestRequests.tsx`: حذف استدعاء و state الـ `AcceptedCelebrationModal`، وتوجيه المستخدم مباشرة لصفحة الرحلة فور القبول.
   - في `src/pages/JourneyPage.tsx`: حذف الزر المكرر المشار إليه عبر محدد التركيز (زر العودة السفلي الزائد).

3. **الخطوة 3: تحديث وتجميل خط المراحل (`journey.ts`, `JourneyTimeline.tsx`, `JourneyPage.tsx`)**
   - تبسيط خط المراحل ليكون 3 مراحل + النهاية المكتملة.
   - تحسين التصميم البصري لخط سير الرحلة ليكون مريحاً على الهاتف والشاشات الكبيرة ومتجاوباً.
   - التخلص من أي شاشات أو نصوص متبقية تشير للمراحل السبع القديمة.

4. **الخطوة 4: تطوير أدوات السداد في لوحة الإدارة (`AdminRequests.tsx`)**
   - إضافة قسم مخصص ومرن داخل بطاقة كل طلب في لوحة الإدارة للتحكم في سداد العربون للطرفين.
   - توفير قائمة منسدلة أو خيارات: [مسدد | بانتظار السداد | لم يسدد] + حقل إدخال وتعديل المبلغ المسدد بالريال القطري.
   - حفظ التعديلات فوراً مع تحديث إحصائيات ومرحلة الطلب تلقائياً عند اكتمال السداد.

5. **الخطوة 5: التحقق والبناء النهائي**
   - التأكد من سلامة البناء واجتياز الفحص عبر `compile_applet` و `lint_applet`.
   - اختبار سيناريو إنشاء وقبول الطلب والتأكد من ظهور المبالغ والخطوات بشكل سليم ومطابق تماماً للمطلوب.
